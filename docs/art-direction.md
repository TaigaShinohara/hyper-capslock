# アート方針：ハイパーCapsLock

- 版：0.1
- 決めた日：2026-11-17
- 出どころ：コンセプト・UXからの導出（指定された見た目は無い。直前の UX レビューで残した体験を、今の文書の雰囲気から読み取って固定した）
- 対象：GitHub 上で読む文書。README.md、docs/ の利用者向け文書、mac/ と windows/ の README。設定ファイル（mac/karabiner、windows/kanata、windows/autohotkey）は対象外。

このファイルが正本。文書を足す・直す前にここを読み、渡す前に項目ごとに照合する。利用者向けのページからはリンクしない。入れる人の次の操作ではないため。

## 0. 読み取った事実と、今回決めること

読み取った事実（方針ではない）:

- 装飾が無い。絵文字、色付きバッジ、独自の色は使っていない。
- 文は常体で、短く言い切る。
- 割り当ては表、入れ方は番号の手順、という役割分担が既にある。
- 実機でまだ押していない、と隠さずに書いている。
- 同じキーの書き方、同じ注意の言い方、見出しの強さがページごとに揺れている。

今回決めること:

- 新しい見た目は発明しない。上の雰囲気を正式な方針にする。
- 揃えるのは、見出しの階層、表の形、キーの書き方、用語、注意の囲み、往復の見せ方。
- キーの挙動と設定ファイルは変えない。

## 1. 世界の言葉

- 雰囲気キーワード（3つまで）：正確、静か、一本道
- やらない雰囲気：にぎやか、宣伝、手順が枝分かれして見える、同じ表が何枚もある
- 一文で言うと：開いたページに、押すキーと次の一手だけが静かに置いてある。

## 2. 根拠マップ（コンセプト → アートの選択 → 理由）

コンセプト（UX レビューで推定し、実装済みの判断記録に沿うもの）：AI に指示して開発する人が、CapsLock を起点にチャットとエディタとプレビューを往復する。流れを切らず、既存のショートカットを不用意に壊さない。

| コンセプトの要素 | アートの選択 | 理由 |
| --- | --- | --- |
| 往復の流れを切らない | 往復は1行。割り当て表をその直下で一番重くする | 循環が1回で読めると、次に押すキーが一つに決まる。大きな図は表と主役を取り合わない |
| 既存を壊さない安心 | 押すと困る操作だけ WARNING。まだ確かめていないことは同じ文の NOTE | 注意の色が増えると、どれが本当に危ないか分からなくなる |
| 1個ずつ足す | 手順は番号の一本道。どちらか一方のときだけ A / B | 最初の成功の前に枝が見えると、手が止まる |
| 実機未確認を隠さない | ページごとに違う言い方をやめ、同じ1文の NOTE にする | 言い方が違うと、確認済みのページがあるように見える |
| 割り当て表は1か所 | keymap.md 以外に同じ表を置かない。ほかはリンク | 同じ表が二枚あると、どちらが新しいか分からない |

## 3. 色の性格

GitHub の標準の文字色と背景に乗せる。独自の色コードは持たない。

- 主色の役割と性格：色を足さない。強弱は見出しと表で付ける。彩度を上げる理由が、コンセプト側に無い。
- 補助色の役割：GitHub の NOTE（青）は「まだ押して確認していない」と「開閉なので閉じることがある」。WARNING（赤）は「押すと別のことが起きる」と「レジストリを自分で変える」。
- 背景と文字の関係：背景色や帯は置かない。コード体はキー名だけに使い、文の強調には使わない。
- 色を増やすときの決まり：NOTE と WARNING で役割が足りないときだけ、方針の改定として提案する。
- やらない色使い：TIP、IMPORTANT、CAUTION は使わない。ページごとに注意の色を変えない。太字の色分けをしない。

## 4. 形の言語

- 角丸の方針：持たない。GitHub の標準の表と囲みに任せる。
- 線と境界：区切りは見出し、表、囲みの3つ。水平線（`---`）は置かない。
- 影と立体：置かない。フラットのまま。
- アイコンのタッチ：アイコン、絵文字、バッジは置かない。
- イラスト・写真を使う場合のタッチ：使わない。往復は1行の文にする。色付きの図、影のある図、SVG は、表と主役を取り合うので置かない。

往復の1行の形:

`Hyper+1` エディタ → `Hyper+C` チャット → `Enter` で送る → `Hyper+2` プレビュー（または `Hyper+T` パネル）→ `Hyper+1` エディタ

矢印は `→` だけ。階段状のインデントは循環に見えないので使わない。

## 5. 文字と密度

- フォントの性格：GitHub の標準。個性の出るフォントは足さない。文は常体。ですますにはしない。
- 文字の階層の原則：3段まで。ページの主役（見出し1つと、表か手順のどちらか）＞ 補助（注記は2つまで）＞ 出典は折りたたみ。太字は README の「AIチャット ⇄ エディタ ⇄ プレビュー」だけ。ほかのページで太字を使わない。
- 密度の方針：1ページに重い要素は一つ。割り当て表のページでは表。手順のページでは番号。判断の記録では ID の表。余白は GitHub の見出しに任せ、空行を装飾に使わない。
- 1画面の情報量の目安：開いて3秒で「このページで次に何をするか」が分かる。README は押したときの表。割り当て表は最初に入れるキー。手順書は1番から進む。

見出し:

- H1 はページに1つ。番号を付けない。
- H2 は節。順番にやる手順のページだけ `1.` のように番号を付ける。
- どちらか一方を選ぶ節は `A.` と `B.`。番号にすると両方やるように見える。
- H3 は、その節の中の「最初の成功」と「外し方」だけ。
- H4 は使わない。

用語:

| 使う | 使わない | 理由 |
| --- | --- | --- |
| ハイパーCapsLock | 文書見出しの Hyper CapsLock | 文書の製品名。Karabiner の一覧に出る題は設定の title のまま「Hyper CapsLock」 |
| 最初に入れるキー | 最初の一式、スターターセット | 同じものを指す言い方を一つにする |
| ルール名 `3. スターター` | 説明文の中の曖昧な「スターター」 | 画面に出る名前はそのまま残す |
| 第2弾 | フェーズ2、Phase 2 | 文書側の名前。設定の `Phase2` は変数名なので変えない |
| 長押し | ホールド | 定義とルール名。手順の動詞は「押したまま」 |
| すぐ離す | タップ、単押し（手順の中） | 手順は手の動きで書く。ルール名の「単押し」は画面の言葉として残す |
| 最初の成功の動詞も「すぐ離す」 | 叩く | 入口と手順で動詞を分けない |
| 大文字固定 | 大文字のまま | 同じ状態の名前を一つにする |
| アプリの切り替え | アプリ切替 | 送り仮名を揃える |
| 開閉 | トグル | 既に使っている日本語に合わせる |
| 割り当て表 | キーマップ（見出し） | ファイル名 keymap.md は変えない。見える題は割り当て表 |
| 確認の手順 | テスト | リンクの文言。ファイル名 TESTING.md は変えない |
| 判断の記録 | 決定ログ | リンクの文言 |
| Office キーを自分で止める | Office キー無効化 | リンクの文言。任意であることが題に残る |

画面に出る英語のボタンとメニューは「」で囲む。コード体にはしない。例：「Enable」「Add predefined rule」「Record Hotkey」。

## 6. 表記トークン

値の色コードは無い。揃える値はキーの書き方。

| 種類 | 書き方 | 例 |
| --- | --- | --- |
| この keymap の操作 | `Hyper+` の直後にキー。空白なし | `Hyper+C`、`Hyper+1`、`Hyper+Enter` |
| 同じ Hyper+ の列挙 | 先頭だけ Hyper+。スラッシュの前後に空白 | `Hyper+H` / `J` / `K` / `L` |
| 物理キー | 英語名をコード体 | `CapsLock`、`Esc`、`Enter`、`Space` |
| 記号キー | 日本語名をコード体 | `Hyper+ピリオド` |
| macOS へ送る修飾 | `Command` `Control` `Option` `Shift` を `+` で結ぶ | `Command+L` |
| Windows へ送る修飾 | `Ctrl` `Alt` `Shift` `Win` を `+` で結ぶ | `Ctrl+L`、`Win+1`、`Win+←` |
| 両 OS を並べる | スラッシュの前後に空白 | `Command+L` / `Ctrl+L` |
| 時間 | 文書はミリ秒 | `200ミリ秒` |
| ツールが画面に出す名前 | そのままコード体 | `escape`、`left_command`、`caps_lock` |
| ルール名 | 画面の文字列をコード体 | `1. コア` |

使わない書き方：`Cmd`、`Caps+C`、`CapsLock+C`、`Hyper + C`（空白あり）、文書の中の `200ms`。

設定ファイル側のコメントはツールの記法のままにする（Kanata の `C-l`、`200ms`）。文書に合わせて書き換えない。挙動のファイルを開いて直さない、がこの方針の境界。

## 7. 動きの性格

- 動きの性格：動かさない。
- 動きを入れてよい場面：無い。折りたたみは、公式の出典を表と競合させないための開閉であり、演出ではない。使う場所は割り当て表の「公式の資料との対応」だけ。
- やらない動き：点滅、アニメーション、自動で開く折りたたみ、カーソルを追う装飾。
- 動きを減らす設定への対応：動きが無いので、特別な対応は要らない。

## 8. 画面の意味

全体:

- 一番見せたいもの：CapsLock を起点にした往復で、最初に押すキー。
- どう思ってほしいか：押す前に結果が読め、次の一手が一つに決まる。
- それを実現する主な手段：ページごとに重い要素を一つにし、キーの書き方をトークンに固定する。

| ページ | 一番見せたいもの | どう思ってほしいか | 主な手段 |
| --- | --- | --- | --- |
| README.md | すぐ離すと `Esc`、押したままは Hyper | 自分向けで、最初の一手が分かる | 冒頭の一文と、表は一つ。割り当て全表は置かない |
| docs/keymap.md | 最初に入れるキーの表 | OS が違っても同じ行で読める | 5列の表。往復は1行。出典は折りたたみ |
| docs/TESTING.md | 今やる確認と、その期待 | 期待と違ったら止めていい | 番号。キーを押す手順だけ「期待:」 |
| docs/decisions.md | 採用した対応 | なぜ送らないかが追える | ID の表。利用者向けの言い方に揃える |
| docs/windows-office-key.md | 通常はやらない。やるなら危険なコマンド | 打つ前に危ないと分かる | WARNING をコマンドの前に置く |
| mac/README.md | 最初の成功までの一本道 | ルールを全部押さなくていい | 番号。最初に「Enable」するのは2つだけ |
| windows/README.md | Kanata での最初の成功 | 片方だけでいい | A を推奨として先に、B は代替。同時にやらない |
| mac/raycast/README.md | 任意の Q と W だけ | Hyper Key とは別物だと分かる | 2行の表。最初に入れるキーの表は複製しない |

## 9. 良い例／悪い例

良い例（読み取り時点で、方針に合っていたもの）:

- README の冒頭。タイピングではなく往復、と言い切っている。
- keymap.md の5列。macOS と Windows の差が同じ行にある。
- 常体で、宣伝の文が無い。

悪い例（読み取り時点のズレ。この版の作業で直す）:

- `Cmd+L` と `Command+L`、`Caps` と `CapsLock`、`CapsLock+C` と `Hyper+C` が混在する。
- 「最初の一式」「スターター」「最初に入れるキー」が同じものを指す。
- 往復が階段のインデントで、循環に見えない。括弧の注意が行の中に入り、一周のリズムを切る。
- 実機未確認の文がページごとに違う。
- windows/README.md の「とは書かない。出典が無い。」は、編集者への注意が利用者のページに残っている。判断の記録に既にある。
- 公式資料の長い箇条書きが、割り当て表と同じ強さで続いている。

直すときは情報を足さない。表記を揃え、同じ注意を同じ囲みにし、出典を畳み、利用者の次の操作に効かない文を削る。
