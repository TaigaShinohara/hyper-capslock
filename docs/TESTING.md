# 実機で確認する手順

下の番号を上から行う。期待と違ったら、そこで止めて、次のキーは足さない。

Mac と Windows の実機では、まだ押して確認していない。

`Hyper+C` は、`CapsLock` を押したまま C を押す。ほかの `Hyper+` も同じ。

共通の期待:

- 生成中に `CapsLock` をすぐ離しても、生成は止まらない。
- 変更の提案が残っているときに、`CapsLock` をすぐ離す、`Hyper+C`、`Hyper+T`、`Hyper+1` を押しても、全部承認にも全部却下にもならない。
- `CapsLock` を1秒押して、何も押さずに離しても、Office もスタートメニューも開かない。
- `CapsLock` を押したまま 200ミリ秒以内に、割り当てていない `Space`（macOS では H は隠すことがあるので `Space`）を押して離しても、`Esc` は出ない。第2弾を入れる前の H でも、`Esc` は出ない。Kanata の右 Alt は、この確認に使わない。長押しの判定の対象外。

## macOS ネイティブアプリ

1. 標準のキーボードで初回画面を開く。権限を許可したあとも、有効にするまでは CapsLock の動作が変わらないことを確認する。「有効にせず設定を開く」でも停止中になる。
2. 検証用の環境で CapsLock → Control、CapsLock に関係しない HID 割り当て、既存の F19／F20 割り当てをそれぞれ用意する。既知の競合時は案内が出る。他のキーボードを選び、初回の試用と一時停止、二度目の停止、終了で元の設定が維持されることを確認する。
3. 複数台で、選んだキーボードの CapsLock だけが変換されることを確かめる。デバイスが外れたり、使用中の割り当てが変更されたりした場合は停止して問題を表示する。再接続しただけでは変換を適用しない。
4. JIS の「英数」だけを使う場合は CapsLock が変わらないことを確認する。別の設定ツールで CapsLock を変換している場合は、初回が失敗してもキー選択に戻るか停止できることを確認する。
5. 通常の Esc ではガイドの成功表示が出ない。ガイドを前面にして選んだキーを短く押すと Esc の受信を表示する。数字の試用では、指定したアプリが実際に前面になったときだけ成功を表示する。
6. C と T はそれぞれ独立してオン・オフできる。外部転送は既定でオフ。転送をオンにし、C／T をオフにした場合は未割り当てとして送られることを確かめる。ピリオドは送られない。

## 1. macOS・US 配列

1. [macOS の手順](../mac/README.md) で、ルール `1. コア` と `2. 安全` だけを「Enable」する。`3` 以降はまだ「Enable」しない。
2. Karabiner-EventViewer を開く。
3. `CapsLock` をすぐ離す。期待: `escape` の key down と key up が出る。`caps_lock` のランプは点いたままにならない。
4. `CapsLock` を1秒押したままにする。期待: `left_shift`、`left_command`、`left_control`、`left_option` の4つが、押しているあいだ同時に down のまま。`left_command` だけ、にはならない。離すと4つとも up。`escape` は出ない（200ミリ秒を超えて押しているため）。
5. Finder を前面にして、`CapsLock` を押したままピリオドを押す。期待: 診断ファイルのフォルダは開かない。Apple の手順では、Finder が前面のとき `Command+Option+Shift+Control+ピリオド` で sysdiagnose が始まる。https://podcasters.apple.com/assets/Mac-sysdiagnose-logging-instructions.pdf
6. 割り当てが無いキーは、`Command+Control+Option+Shift` と一緒にアプリへ届く。Q、W、H は押さない。
7. ルール `3. スターター` と `4. スターター` を「Enable」する。ルール `4. スターター` のアプリ名を、自分のブラウザとターミナルに変えてから「Enable」する。
8. Cursor を前面にして、チャット欄を閉じた状態で `Hyper+C`。期待: サイドパネルが開く。もう一度押すと閉じる。閉じるのは不具合ではなく、公式の開閉どおり。
9. エディタで文字を選択した状態で `Hyper+C`。期待: 全部承認や全部却下にはならない。開閉になるか、選択が新しいチャットに追加されるかは、公式ページに両方書いてあるので、出た方をメモする。
10. ブラウザを前面にして `Hyper+C`。期待: アドレスバーには行かない。Cursor が前面に来る。
11. Cursor を前面にして `Hyper+T`。期待: 下のパネルが開閉する。バッククォートの文字は入力されない。
12. `Hyper+1`。期待: Cursor が前面に来る。`Hyper+2` と `Hyper+3` は、名前を変えたアプリが前面に来る。名前が違うと macOS がエラーを出す。

## 2. macOS・JIS 配列

1. 手順 1 の 1〜6 のあとで行う。ルール `6. 任意・JIS` はまだ「Enable」しない。
2. EventViewer で、`CapsLock` の位置のキーと、スペースの左にある英数キーを、それぞれ1回押す。
3. `caps_lock` と出たキーだけを、ルール `1. コア` に任せる。`japanese_eisuu` と出たキーを Hyper にしたいときだけ、ルール `6. 任意・JIS` を「Enable」する。両方のキーを Hyper にしたくないなら、出なかった方のルールは「Enable」しない。
4. 英数キーを `Shift` と一緒に押したときの本来の動作（大文字固定になるキーボードがある）は、ルールを「Enable」すると上書きされる。大文字固定が要るあいだは、そのルールを外す。
5. 手順 1 の 7〜12 と同じ期待で、チャット、パネル、アプリの切り替えを見る。`Hyper+T` でバッククォートは出ない。

## 3. Windows・US 配列（Kanata）

AutoHotkey は起動しない。

1. タスクバーの左から、1番に Cursor、2番にブラウザ、3番にターミナルをピンする。
2. [Windows の手順](../windows/README.md) の Kanata を入れ、`--check` のあとで起動する。
3. Cursor のチャット欄にカーソルがある状態で、`CapsLock` をすぐ離す。期待: 入力欄からフォーカスが外れる。大文字固定にはならない。
4. `CapsLock` を1秒押して離す。期待: Office、Word、Teams、LinkedIn、スタートメニューは開かない。
5. ブラウザを前面にして `Hyper+C`。期待: これは安全ではない。`Ctrl+L` がブラウザに届く。アドレスバーに行くことがある。そのときはすぐ `Esc`。以降、`Hyper+C` と `Hyper+T` は Cursor が前面のときだけ押す。
6. `Hyper+1`。期待: 1番にピンした Cursor が前面に来る。続いて `Hyper+C`。期待: チャットのサイドパネルが開閉する。
7. Cursor が前面で `Hyper+T`。期待: 下のパネルが開閉する。バッククォートは出ない。
8. `Hyper+Q`、`Hyper+W`。期待: 今のウィンドウが左半分、右半分になる。Word は開かない。
9. 第2弾の H などは、ファイルを編集するまで何もしない（文字も出ない）。

## 4. Windows・US 配列（AutoHotkey）

Kanata を終了してから行う。両方は同時に動かさない。

1. ピンの位置は手順 3 と同じ。
2. `HyperCapsLock.ahk` をダブルクリックする。Kanata が残っていると、メッセージを出して終了する。それが期待どおり。
3. 手順 3 の 3、4、6、7、8 と同じ期待。
4. ブラウザが前面のとき `Hyper+C`。期待: `Ctrl+L` は送らない。タスクバーの1番（Cursor）が前面に来る。チャットは、前面になってからもう一度 `Hyper+C` で開閉する。
5. ブラウザが前面のとき `Hyper+T`。期待: 何も起きない。
6. トレイのアイコンを右クリックして終了すると、`CapsLock` は元に戻る。

## 5. Windows・JIS 配列

US の確認が通ってから、同じキーボード設定のまま JIS 用の入力（Microsoft IME など）に切り替えて行う。Kanata と AutoHotkey は別々に、片方ずつ。

1. AutoHotkey のトレイアイコンを右クリックし、「Open」→「View」→「Key history」を開く。英数 / `CapsLock` の位置を押して離す。
2. 期待してよいのは「押した通知と、離した通知の両方が出ること」だけ。公式の説明では、一部の IME は `CapsLock` を飲み込んで、AutoHotkey から見えなくする。離した通知が来ない、またはキーが見えない場合は、そのキーボードではこのスクリプトを使わない。レジストリのスキャンコード書き換えは、このリポジトリでは行わない。
3. 離した通知が来た場合だけ、手順 3 と手順 4 の期待（Office が開かない、チャットは Cursor が前面のときだけ）を繰り返す。
4. Kanata は、起動コマンドに `--debug` を足して、同じキーを押す。ログに `caps` が出ない場合は、そのキーボードではこの設定ファイルを使わない。出た場合だけ、Office が開かないことと、`Hyper+T` でバッククォートが出ないことを見る。
5. 60秒より長く押し続けたとき、AutoHotkey は Hyper を自分から解除する。これはキーを離した通知が来ない場合の安全策で、実機での成否は未確認。

## 6. Cursor の状態

US 配列で、使っている OS の推奨手順（macOS なら Karabiner、Windows なら Kanata）のまま行う。

1. 待機中（生成していない、変更の提案も無い）。チャットを閉じた状態で `Hyper+C`。期待: サイドパネルが開く。もう一度で閉じる。
2. 生成中。`CapsLock` をすぐ離す。期待: 入力欄から出るが、生成は続く。止まらせたいときは、チャット欄の停止ボタンを使う。`Command+Shift+Backspace` は押さない（提案があると同じキーが全部却下になる）。
3. 変更の提案が残っている。`CapsLock` をすぐ離す、`Hyper+C`、`Hyper+Enter`（割り当てなし）、`Hyper+T` を押す。期待: ファイルの提案は承認も却下もされない。
4. 管理者として開いたターミナルやエディタが前面のとき、`Hyper+1` と `Hyper+T`。期待: 効くとは限らない。AutoHotkey の公式 FAQ では、昇格したウィンドウは昇格していないスクリプトから操作できない。Kanata の LLHOOK 版が同じかは未確認。効かなければ、そのウィンドウはマウスで操作する。
